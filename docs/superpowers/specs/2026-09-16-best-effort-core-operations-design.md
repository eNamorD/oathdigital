# Best-Effort Core Operations

> Status: approved in-chat design, awaiting review of this written spec. This is a prerequisite to [Search on the Procedure Walker](2026-09-16-search-walker-design.md). No production implementation is authorized by this document alone.

## Goal and boundary

Apply the rulebook's “do as much as possible” ruling to core operation execution, not to Dazzle alone. An operation that cannot perform a legal effect may do a smaller counted effect or no effect. A required operation must perform exactly what it requests. Malformed descriptions, inconsistent state, and executor failures are never silently skipped. This is one deliberate breaking change to `OperationPipeline.run` and its callers, not a parallel pipeline or an incremental migration of strict callers.

The pipeline operates on executable `CoreOperation`s. The `Operation` root and tree-control nodes do not carry action-wide requiredness; a `Sequence`, `Branch`, or `BuildOps` does not make its children required. A procedure marks individual operations required where its rules demand them. “May” is a player choice, not a reason to suppress a valid operation.

## Operation interface and defaults

Add `def required: Boolean = false` to `CoreOperation`. An executable operation may override its type default. Add a constructor field only to types for which a caller needs per-instance choice; for example, `SpendSupply(player, amount, required: Boolean = true)` can be used with `required = false` for “enemy players each lose 1 Supply,” and a chosen adviser `Discard.Denizen(..., required = true)` cannot be skipped. A normal Dazzle `Discard.Denizen(...)` uses the false default. This is a field on the operation, not an `OperationAttempt` wrapper.

Replace signed `AdjustSupply` with positive-amount `GainSupply` and `SpendSupply`. `GainSupply` defaults to optional. `SpendSupply` defaults to required and permits per-instance override. `PayCost` is always required and atomic; it cannot be marked optional or partially paid. `Draw` defaults to required because its explicit card IDs and top-first order are authoritative; a procedure that allows a shorter draw constructs a `Draw` with the actual available cards. `Exchange` defaults to required and remains atomic. `Replace` defaults to optional, with its removed and replacement warband counts reduced together. Other operations default to optional unless a rule or accepted player choice makes that use required. Search's payment, draw, Visions Drawn advancement, and accepted placement or replacement must be required. A type default is not a substitute for procedure-specific requiredness.

## Validation and resolution

`OperationValidator` reports typed reasons against each operation's staged input state. Keep current stable error codes and details while distinguishing a rule-impossibility from an invalid operation. A rule-impossibility includes discard immunity and insufficient available counted pieces or Supply. A missing card at its claimed source, illegal destination, invalid stack position, malformed amount, incompatible operation, failed allowlist, or inconsistent state is invalid and rejects regardless of `required`. Contextual `OperationRestriction`s must actually participate in staged validation and reporting; the current validator accepts the vector but does not evaluate it. Provide a walker-facing way to supply catalog-backed restrictions to the pipeline. A reusable discard restriction reports immunity without naming Dazzle, and the pipeline does not embed a power ID.

One resolver uses the validator's typed reasons to find the maximal legal effect of each optional counted operation against the staged state. Every optional counted operation may reduce its requested effect count to the available legal amount, subject to the operation's semantic invariants. Counts that describe existing state, such as the favor and secrets recorded on a discarded card, are not reducible requests; a mismatch is invalid. A linked operation such as `Replace` reduces its linked counts together; it never executes one leg alone. `PayCost` never shrinks, and required operations never shrink. If the maximal count is zero, or a non-counted optional effect is rule-impossible, skip the whole operation. Revalidate any reduced operation before execution. Do not classify an arbitrary executor error as rule-impossibility or use the initial-state `validateBatch` report for authoritative filtering.

`OperationPipeline.run` is the sole staged execution path and returns `OperationRun(state, executed, skipped)`. `executed` contains actual operations, including reduced counts. `skipped` contains the requested operations and typed reasons for command-time inspection. Each successful operation changes the staged state before the next is assessed. An input batch with no operations remains an error; a nonempty batch whose operations all skip succeeds with unchanged operation state. The owning procedure's `update` and the post-state invariant run once after the fold. Any required rejection, invalid operation, executor error, update error, or post-state failure rejects the whole command atomically. Existing callers must adapt to the new result in this prerequisite change; no old strict `run` variant remains.

## Recording and replay

`required` is command-time execution policy, not game state. After an operation executes, canonicalize it to the actual count and its type-default `required` value before adding it to `OperationRun.executed`. This makes in-memory recorded events equal to their encode/decode round trips even when a caller overrode `required`. The journal codec never writes a `required` field. Walker delta steps contain only canonical executed operations; an all-skipped `BuildOps` batch records no delta step. Skip reasons are returned to the command caller, not persisted. Replay applies recorded operations directly and does not consult current catalog restrictions, recalculate counts, or run the best-effort resolver.

`GainSupply` and `SpendSupply` receive separate operation and wire spellings. The existing signed `AdjustSupply` constructor, pattern matches, validator/mutator arms, walker step meaning, Travel cost transforms, and tests are updated in one prerequisite change. Pre-release old-journal compatibility is not required by the existing walker design.

## Verification

Tests cover optional partial gains and spends, zero-available skips, optional `Replace` shrinking both counts together, required costs and draws rejecting instead of shrinking, atomic `PayCost` and `Exchange`, discard immunity beside a legal discard, structural errors beside legal attempts, staged-state changes affecting later operations, and all-skipped versus empty input batches. Assert recorded operations contain actual counts and no skipped operations; encode/decode preserves full event equality; replay reproduces state without running restrictions. Run existing tests for every pipeline caller, including Travel, Recover, Forge, Rest, legacy actions, modifiers, wire codec, and walker projections, plus full backend and architecture gates.
